## 🛠️ 工具系统设计

### 一、核心接口

工具系统的核心在 `internal/tool/tool.go`，定义了一个极简接口：

```go
type Tool interface {
    Name() string                    // 工具名称，如 "Read"、"Bash"
    Description() string             // 工具描述，给 AI 模型看
    Run(ctx context.Context, input json.RawMessage) (string, error)  // 执行工具
    InputSchema() json.RawMessage   // JSON Schema，描述输入参数格式
}
```

设计特点：
- **4 个方法，极其精简**，任何新工具只需要实现这 4 个方法
- **Run 是双向解耦的**：入参是 `json.RawMessage`，出参是 `string`，不依赖具体类型
- **InputSchema 是给模型看的**：模型通过 schema 知道该传什么 JSON 参数

---

### 二、注册中心（Registry）

在 `internal/tool/register.go` 中：

```go
type Registry struct {
    tools map[string]Tool     // 工具名 → Tool 的映射
}

func NewRegistry() *Registry
func (r *Registry) Register(tool Tool)     // 注册工具
func (r *Registry) Get(name string) (Tool, bool)  // 按名查找
func (r *Registry) Describe() []string      // 生成工具描述给 System Prompt
```

**关键方法 `Describe()`**：
- 遍历所有已注册工具
- 拼接成 `"工具名: 描述 input_schema=..."` 格式
- 这些字符串被注入到 **System Prompt** 中，让 AI 模型知道有哪些工具可用

### 四、安全机制（三层防御）

以 **Bash 工具** 为例，展示了完整的安全设计：

```
命令输入
    │
    ▼
① 命令黑名单预检 ← 正则匹配：rm -rf, mkfs, fork bomb 等
    │
    ▼
② 工作目录沙箱 ← filepath.Rel 校验不能逃出 Root
    │
    ▼
③ 强制超时 + 输出截断 ← 32KB 输出上限，超时后 kill 进程组
    │
    ▼
结果输出（含退出码）
```

**路径沙箱** 由 `internal/tool/file/path.go` 统一实现：
```go
func resolvePathWithinRoot(root, target string) (string, error) {
    // 解析绝对路径
    // 用 filepath.Rel 判断是否逃出 root
    // 如果 rel 以 ".." 开头则拒绝
}
```

```go
registry := tool.NewRegistry()

- 新增工具只需 **1 行注册代码**，不需要改动任何核心逻辑

### 六、工具调用链（在 Runner 中）

```
模型输出流式文本
    │
    ▼
Runner.consumeStream()  →  持续接收 Delta
    │
    ▼
Runner.finalizeAssistantMessage()
    │
    ▼
parseAssistantMessage()  →  从文本中提取 tool_use 信封
    │   (支持 4 种格式：裸JSON / fenced JSON / 嵌入文本 / <invoke> 标签)
    ▼
Runner.runToolCall()
    │
    ├─ ui.OnToolCall()  →  通知 UI
    │
    ▼
Runner.executeToolCall()
    │
    ├─ registry.Get(call.Name)  →  查找已注册工具
    ├─ tool.Run(ctx, input)      →  执行
    │
    ▼
结果 → buildToolResultMessage()  →  回灌到历史，继续调用模型
```

**工具调用的 4 种解析格式**（在 `extractToolUseEnvelope` 中）：
1. **裸 JSON**：`{"type":"tool_use","name":"Read","input":{...}}`
2. **Fenced JSON**：`` ```json\n{"type":"tool_use",...}\n``` ``
3. **嵌入文本**：文本中找第一个平衡的 JSON 对象
4. **`<invoke>` 标签**：`` <invoke name="Read"><parameter name="file_path">main.go</parameter></invoke> ``

---

### 七、关键设计理念

1. **工具和 UI 解耦**：工具只返回 `(string, error)`，UI 渲染由外层处理
2. **工具和 Loop 解耦**：Loop 只通过 `registry.Get(name)` 查找工具，不关心具体实现
3. **统一的错误格式**：工具执行失败时，结果中包含 `IsError=true`，让 AI 模型自己判断下一步
4. **安全的默认值**：Bash 有默认 30s 超时，所有文件工具有路径沙箱

**第 1 步**：创建工具文件，实现 `Tool` 接口的 4 个方法：

registry.Register(&mytool.MyTool{Root: root})

```

func renderContextBar(used, cache, limit int) string {
    limit = maxInt(1, limit)
    usedCells := int(math.Round(float64(clampInt(used, 0, limit)) / float64(limit) * 40))
    cacheCells := int(math.Round(float64(clampInt(cache, 0, used)) / float64(limit) * 40))

    var out strings.Builder
    for i := 0; i < 40; i++ {
        switch {
        case i < cacheCells:
            out.WriteString(contextCacheStyle.Render("▰"))  // ← 黄色 ▰ 表示缓存的 token
        case i < usedCells:
            out.WriteString(contextUsedStyle.Render("▰"))   // ← 蓝色 ▰ 表示非缓存的 token
        default:
            out.WriteString(contextFreeStyle.Render("▱"))   // ← 灰色 ▱ 表示剩余空间
        }
    }
    return out.String()
}

## 根因详细分析

### 1. DeepSeek API 行为

DeepSeek 的流式 API 在 SSE 流中**不推送 `usage` 事件**。它在每个 data chunk 中只包含 `choices[].delta`，只有在你调用**非流式接口**时才会在最终响应里返回 `usage`。

但是项目的流式解析代码在 `stream.go` 中：

```go
// stream.go 第 124-131 行
func emitChunkEvents(ctx context.Context, chunk chatCompletionsStreamResponse, events chan<- StreamEvent) (done bool) {
    if chunk.Usage != nil {          // ← DeepSeek 流式响应里永远为空
        // ...
    }
    if len(chunk.Choices) == 0 {
        return false
    }
    delta := chunk.Choices[0].Delta.Content
    // ...
}
```

由于 DeepSeek 流式响应的每个 chunk 中 `usage` 字段永远为 `nil`，所以 `runner.usageKnown` 始终 `false`，`CacheTokens` 永远为 0。

### 2. 对比其他实现的做法

开源项目解决这个问题的方式通常有三种：

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| **双请求** | 先发一次非流式请求仅获取 token 计数，再做流式请求 | 准确但浪费 |
| **末尾拼接** | DeepSeek 在最后一个 chunk 的 `choices[0].finish_reason` 非空时，会在同一 chunk 的嵌套字段里附带 usage | 需要按 DeepSeek 文档特判 |
| **本地估算** | 用 tokenizer 库（如 `tiktoken-go`）本地计算 | 最可靠但不等于真实计数 |
